# Programme intent

`programme_read` and `programme_save` operate on `programme.json` in the explicitly
registered operation root. They do not require `project.yaml`, load providers,
resolve credentials, execute sources or modify any project in the programme.

Read accepts `{ "id": "retail" }` and returns `{ document, digest }`, both null
when no programme exists. Save accepts the same ID, `expectedDigest` (null only for
creation) and an `ingestron.programme/v1` document. Save requires `allowWrite`.

The document contains name, objective, sponsor, stakeholder names/roles, stable
planned-project IDs and requirements with owner, priority, disposition, acceptance
criteria and project references. Ready means ready for review, not approved or
complete. Stakeholder assignments grant no access permissions. Existing arbitrary
role text remains valid for compatibility; clients may offer a predefined role set.

Schema checks enforce bounds, unique IDs, reference integrity and a description,
owner and acceptance criteria for ready requirements. A whole document is limited
to 512 KiB. Identity must match the registered ID on both read and save. No caller
path is accepted. Read/save reject symbolic-link destinations. Save takes an
exclusive `.programme-write.lock`, checks the current digest, writes a private
file and atomically replaces the old version. A stale lock requires operator
inspection after a crash; it is never silently removed while another writer may
be active. Concurrent direct filesystem editors must coordinate writes; the lock
coordinates core operations, not third-party editor behaviour.

This is offline planning intent. It neither compiles project delivery plans nor
calculates evidence-backed progress or programme milestones. Requirements text is
never executed. Local installed CLI/core candidate acceptance is recorded in the
private Studio 2 repository; public release/version pins remain unchanged.

## Work hierarchy and integration identity

Optional `kind` distinguishes epic, requirement, task and milestone; omitted kind
retains legacy requirement semantics. `parentId` allows requirement → epic and
task → requirement/epic. `milestoneId` references an independent milestone and
`due` is an ISO calendar date. Invalid/self/unknown parent links are rejected.

`area` references this programme ID, a named entry in `platforms`, or an entry in
`projects`. Missing area means programme scope. `projectIds` supports additional
cross-project links. Reference integrity prevents removing linked areas or items.
`disposition` supports draft, ready, active, done and deferred; these are manually
recorded intent states, not evidence-derived execution status. Ready/active/done
requirements require owner, description and acceptance criteria.

Optional `externalRefs` store system (jira/azure-devops), container, item ID and
revision separately from local IDs. Duplicate remote identities are rejected.
This metadata does not implement synchronisation, remote access, mapping rules,
conflict resolution or remote deletion. Installed archives exercise round-trip
preservation of these fields. Public package pins remain unchanged.

`programme_project_template` is a pure proposal operation for Full data product v1.
It accepts the current validated document, new project, shared platform, owner and
template identity. It adds explicitly scoped draft work and dependencies without
filesystem writes. Scope-derived IDs reuse platform setup across projects. A later
`programme_save` persists the result with normal revision protection. The schema
rejects unknown/self/duplicate dependencies and cycles; referenced items cannot be
removed. Opaque workspace project identities are supported. Project definitions,
engineering assets and reviewed project delivery plans are not generated by this step.

Policy and Standard records extend the requirement catalogue without changing existing
IDs. Optional people names provide a reusable programme directory. Project areas may
reference their shared platform. `programme_project_template.selectedRecordIds` creates
project-owned tasks with source `basisIds`, copies acceptance criteria and records a
Planned application for each selected requirement, policy or standard. Verification
depends on these tasks. Invalid/dangling/duplicate catalogue references are rejected.

Per-project application is separate from work disposition: Planned, Applied or Not
applicable. Applied requires an evidence note/reference, and Not applicable requires a
reason. These are recorded planning assertions, not enforced or independently verified
compliance. Catalogue edits do not regenerate existing plans. Ordinary programme CAS
save remains the only persistence operation; there is no database or remote sync.

## Platform configuration and local credentials

`platforms[].configuration.targets` holds independent Fabric, Databricks and ADF
profiles: desired capabilities/policies, naming patterns and named environments.
The catalogue is curated local product metadata, not a live tenant inventory.
`programme_platform_catalogue` reads this catalogue without writing. Existing
`programme_save` validates and persists profiles with revision protection. Unknown
provider keys, naming tokens and authentication types are rejected. These settings
do not yet drive compiler output or enforce cloud configuration.

Environment configuration accepts declared non-secret fields. Secrets are strict
references to `local-env`, Azure Key Vault URL/name, or Databricks scope/key. Scope
references require Databricks; local references require a development environment.
No inline value is accepted in the shared document. `programme_secret_status`
reports presence only. `programme_secret_set` requires write permission, a declared
local reference and a single-line value passed through CLI stdin. It never returns
the value. Names that could alter process execution are reserved.

The host sets `INGESTRON_LOCAL_SECRETS_DIR`; direct CLI use defaults to
`~/.config/ingestron/local-env`. Storage is namespaced by canonical programme root,
programme ID, platform, provider and environment. Values use shell-quoted assignments
in `local.env`, owner-only directories (0700) and files (0600), a write lock and atomic
rename. Symlinks, hardlinked files and permissive file modes are rejected. POSIX file
permissions are required to write; Windows users must supply OS environment variables.
This is private plaintext storage, not encryption or a vault.

Removing a reference does not delete its stored value. There is no readback, remote
secret retrieval, process-environment injection, cloud mutation or secret deletion
operation in this increment. A later execution adapter must explicitly resolve the
selected environment and credential references; persistence is not runtime activation.

## Generation defaults catalogue

`platforms[].configuration.targets[].generation` is an optional, provider-specific
map of generation decisions. Unknown fields or option IDs are rejected. The catalogue
returns available choices, conservative defaults and a source-audited provider/planned
support distinction. This is not installed-provider introspection or cloud qualification.

Programme read/save responses include computed `generationReviews` for saved profiles.
Reviews identify the selected choice, a provider mapping where one exists and conflicts
with disabled prerequisite capabilities. Older documents without generation choices
remain valid; an absent programme retains its original null snapshot shape. Reviews
are not persisted in the programme document and do not contain credential values.

These choices are authoring intent. Applying them to project definitions is planned,
so the review always reports that binding separately from existing provider support.
The shared defaults do not alter planner behaviour, replace reviewed flow/source
semantics, override project policy or silently fall back from a planned option.
